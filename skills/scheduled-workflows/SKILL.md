# Scheduled Workflows

Use this skill before any OpenCTO scheduled workflow action. This includes
`WorkflowCreate`, `WorkflowUpdate`, `WorkflowDelete`, every `WorkflowOperation`
action, and direct edits under `$OPENCTO_WORKSPACE/workflows/{workflow_id}`.

## Source Of Truth

The source of truth for a workflow is only:

```text
$OPENCTO_WORKSPACE/workflows/{workflow_id}/
```

This directory is a workflow-local Git repository. The scheduled workflow points
to a committed hash from this repository. Runtime run directories, artifacts,
logs, caches, and generated outputs are not source of truth.

## Directory Layout

```text
$OPENCTO_WORKSPACE/
  workflows/
    {workflow_id}/
      workflow.yml
      src/
      .git/
      .gitignore
  workflow-runs/
    {workflow_id}/
      {run_id}/
        workflow.yml
        src/
        state.json
        artifacts/
          {step_id}/
        steps/
          {step_id}/
            attempt-{n}/
              stdout.log
              stderr.log
```

`workflows/{workflow_id}/workflow.yml` is the editable manifest. It defines the
workflow name, description, schedule, notification policy, global env, and
ordered steps.

`workflows/{workflow_id}/src/` contains workflow-owned implementation files.
Edit source code here.

`workflows/{workflow_id}/.git/` contains the workflow-local Git history used by
scheduled workflow commit hashes. Do not edit it directly.

`workflows/{workflow_id}/.gitignore` is generated by OpenCTO. It tracks
`workflow.yml` and `src/` while keeping runtime outputs and dependency caches out
of Git.

Ignored paths such as `artifacts/`, `steps/`, `output/`, `tmp/`, `temp/`,
`.cache/`, `node_modules/`, `venv/`, `.venv/`, `__pycache__/`, and
`.pytest_cache/` are not durable workflow source.

`workflow-runs/{workflow_id}/{run_id}/` is a per-run snapshot extracted from the
scheduled commit. Treat it as runtime evidence only, not editable source.

`workflow-runs/{workflow_id}/{run_id}/state.json` records run and step status,
step commands, attempts, log paths, output summaries, and failure details.

`workflow-runs/{workflow_id}/{run_id}/artifacts/{step_id}/` stores files written
by a step for later steps in the same run.

`workflow-runs/{workflow_id}/{run_id}/steps/{step_id}/attempt-{n}/stdout.log`
and `stderr.log` contain per-attempt step logs.

## Before Any Workflow Action

Identify the target `workflow_id` before acting.

If the target workflow is ambiguous or the user asks for a read/control
operation, use `WorkflowOperation`:

```text
WorkflowOperation operation=list
WorkflowOperation operation=describe workflow_id=<workflow_id>
```

For delete, pause, resume, trigger, or any action that affects a schedule, use
`WorkflowOperation operation=describe` before the action unless the current turn
already contains a fresh description for the same workflow.

## Before Editing Or Updating

Before `Edit`, `Write`, or `WorkflowUpdate`, gather live context from the
workflow source directory:

- Read `$OPENCTO_WORKSPACE/workflows/{workflow_id}/workflow.yml`.
- List `$OPENCTO_WORKSPACE/workflows/{workflow_id}/src/`.
- Read the relevant files under `$OPENCTO_WORKSPACE/workflows/{workflow_id}/src/`.
- Run `git -C $OPENCTO_WORKSPACE/workflows/{workflow_id} status --porcelain`.
- Run `git -C $OPENCTO_WORKSPACE/workflows/{workflow_id} log --oneline -n 20`.
- If schedule state matters, use `WorkflowOperation operation=describe`.

Do not edit workflow files before this inspection unless the user asks for a
very small mechanical change and already supplied the exact file and desired
replacement.

## Workflow Design Rules

Each manifest step runs as a Temporal activity. Keep every step single-purpose,
bounded, and safe to retry.

Good steps are idempotent or tolerate repeated execution. They can be retried
without duplicating irreversible external effects. If a step writes external
state, use deterministic keys, upserts, checkpointing, or explicit duplicate
guards.

The manifest defines durable step boundaries only. Implementation files are
ordinary runnable programs, scripts, or binaries invoked by step `command` and
`args`. Do not write schedulers, workers, queues, daemons, or orchestration
framework code inside `src/`.

Use `command` for the executable only and `args` for arguments. Do not repeat
the executable in `args`.

Global `env` entries apply to every step and must be literal `NAME=value`
assignments. Runtime-owned `OPENCTO_*` names are reserved.

During a run, each step executes with the run directory as its working
directory. Runtime environment variables include:

- `OPENCTO_WORKFLOW_ID`
- `OPENCTO_RUN_ID`
- `OPENCTO_RUN_DIR`
- `OPENCTO_STEP_ID`
- `OPENCTO_STEP_DIR`
- `OPENCTO_WORKSPACE`

Write step outputs under
`OPENCTO_RUN_DIR/artifacts/{step_id}/filename.json`, using `OPENCTO_STEP_ID` for
the current step id. Later steps can read files from the same run directory.

## Step State Passing

OpenCTO does not automatically pass business data from one step to the next
through Temporal activity results or template variables.

Step-to-step state is passed through artifact files in the run directory. A step
that produces data should write a named file under its artifact directory:

```sh
mkdir -p "$OPENCTO_RUN_DIR/artifacts/$OPENCTO_STEP_ID"
printf '{"ok":true}\n' > "$OPENCTO_RUN_DIR/artifacts/$OPENCTO_STEP_ID/payload.json"
```

A later step reads that file by the producing step id:

```sh
cat "$OPENCTO_RUN_DIR/artifacts/check/payload.json"
```

Use clear artifact contracts between steps: stable filenames, documented JSON
schemas or simple text formats, and explicit behavior for missing or invalid
artifacts.

`state.json` in the run directory records runtime metadata such as run status,
step status, attempts, commands, log paths, output summaries, and failures. Do
not use `state.json` as the business data interface between steps.

Do not use template syntax such as `{{steps.check.stdout}}` in `env` or manifest
fields. Global `env` entries must be literal `NAME=value` assignments.

## Editing And Updating

Use `Edit` or `Write` for local workflow source files. Keep source changes under
`$OPENCTO_WORKSPACE/workflows/{workflow_id}/workflow.yml` and
`$OPENCTO_WORKSPACE/workflows/{workflow_id}/src/`.

Before `WorkflowCreate` or `WorkflowUpdate`, verify the workflow:

- Re-read changed files if needed.
- Check `git -C $OPENCTO_WORKSPACE/workflows/{workflow_id} diff -- workflow.yml src`.
- Run any lightweight validation or tests that are available for the changed
  source.
- Confirm the manifest still follows the single-responsibility step model.
- When safe, validate with a one-shot/ad hoc workflow run before considering the
  create or update complete. For existing workflows, the schedule commit must be
  current before triggering; if the bundle is dirty or HEAD is unpublished, call
  `WorkflowUpdate` first, then use `WorkflowOperation operation=trigger` for the
  validation run. For new workflows, run local source validation first, then
  after `WorkflowCreate` succeeds, trigger one validation run when it is safe to
  do so.
- If a one-shot validation run could send messages, charge money, modify
  external systems, or otherwise have irreversible effects, ask before running
  it and document the skipped validation if the user declines.

Only after verification succeeds, call `WorkflowUpdate`. `WorkflowUpdate`
validates the bundle, commits dirty workflow changes, and repoints the schedule
to the new commit hash.

Do not run `git commit` manually for workflow bundles.

Before triggering a workflow, make sure it has no dirty local changes and its
scheduled commit hash is current. If there are dirty changes or an unpublished
HEAD commit, call `WorkflowUpdate` before triggering.
